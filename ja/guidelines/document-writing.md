# ドキュメントガイドライン

cortex リポジトリにおけるドキュメントの書き方・管理方針。

---

## 原則

### コードが唯一の真実である

ドキュメントはコードの二次情報に過ぎない。コードと矛盾するドキュメントは害になる。ドキュメントを書く前に、その情報をコード・型・テスト・lint ルールで表現できないか検討する。

### ドキュメントの価値は鮮度に依存する

書いた瞬間が価値のピークであり、時間と共に劣化する。維持コストを払えないドキュメントは書かない。書くなら維持する仕組みも一緒に作る。

### 読者はコードを読める

cortex の docs/ の主な読者は開発者と AI エージェントである。「どう動くか」をコードより分かりやすく説明し直す必要はない。読者が本当に必要としているのは「なぜそうなっているか」と「どこから読み始めればよいか」の 2 つ。

### 判断の優先順位

情報を残したいとき、上から順に検討する。上で表現できるものを下で書いてはいけない。

> この順序は「どの手段で表現するかを選ぶ」際の検討順であり、各手段の重要度を示すものではない。たとえば `@graph-*` アノテーションの欠如は review-guidelines.md で Critical と定義されている。

| 優先度 | 手段 | 理由 |
|--------|------|------|
| 1 | 型定義 | コンパイラが検証。実行時コストゼロ |
| 2 | lint ルール | 毎回実行。file:line で報告。--fix 対応 |
| 3 | テスト | CI で実行。振る舞いをアサーションで記述 |
| 4 | スキーマバリデーション | 境界で実行時に検証 |
| 5 | CI チェック | lint やテストで拾えないものを捕捉 |
| 6 | `@graph-*` JSDoc アノテーション | コードに付与するだけで Product Graph ノードを自動生成。Why・接続先・ドメインを構造化して記録 |
| 7 | 自動生成ドキュメント | コードから派生。再生成で drift を防止 |
| 8 | 手書きドキュメント | 最後の手段。上のどれでも表現できない場合のみ |

## 何を書くか

### Why ドキュメント

「なぜそうなっているか」を記録するもの。コードからは読み取れない意思決定の背景。

### How to get started ドキュメント

**セットアップ手順** — スクリプトで自動化できる部分はスクリプトにして、ドキュメントはスクリプトの実行方法だけ書く。

### アプリケーションドキュメント

各アプリの目的・アーキテクチャ・エンドポイント・設定・デプロイ情報を記述する。

書くべき内容:
- 目的（1-2 文で何をするアプリか）
- アーキテクチャ図（mermaid。データフローの全体像）
- このアーキテクチャを採用した理由（なぜこの構成か、他の選択肢を捨てた根拠）
- 仕組みのポイント（コードを読むだけでは分からない設計上の要点。レート制御の戦略、ページネーションの方式、リトライ設計など）
- インフラ経由の依存先（EventArc、Cloud Scheduler、Pub/Sub 等を介して連携するアプリや pipeline。package.json では追えない暗黙的な依存）
- エンドポイント一覧（テーブル形式）
- 設定（環境変数、pipeline_config フィールド等）
- デプロイ情報（スタック名、Pulumi パス）

### 運用ドキュメント

**review-guidelines.md** — コードレビューの判断基準。自動レビューシステムのプロンプトとしても使われるため、曖昧な表現を避け、判定可能な基準で書く。

**observability.md** — 可観測性基盤の構成と、アラート・ダッシュボードの設計方針。

### プレゼンテーション・共有資料

`docs/sharing/` と `docs/presentation/` に配置する。プレゼン資料はシステムの正確な現状を反映することを目的としていない。設計判断の根拠として参照してはいけない。

## 何を書かないか

### 現在の実装を散文で説明するもの

「このシステムは現在こう動いている」という説明文。コードが変わった瞬間に嘘になる。

代わりに、コードのエントリポイントを示す（「`apps/pipeline/shopify/src/index.ts` から読み始める」）。

### 手書きの API リファレンス

エンドポイントのリクエスト/レスポンス仕様を手書きで維持するもの。OpenAPI スキーマからの自動生成、または型定義からの導出を使う。手書きが必要な場合はエンドポイント一覧（名前・メソッド・役割の 3 列テーブル）に留める。

### 完了した計画をそのまま残すもの

実装が終わった計画書を「実装済み」マーク付きで残し続けるパターン。AI エージェントは区別なく文脈として読み込む。完了した計画は `plans/archived/` に移動する。

### コードのコメントで十分な情報

関数の引数の意味、処理の手順、条件分岐のロジック。これらはコードのインラインコメントや JSDoc で書く。docs/ に分離すると、コード変更時に同期されない。

### 同じ情報の複数箇所への記載

情報の正規の置き場所は 1 箇所。他の場所からはリンクで参照する。

### URL とファイルパスのベタ書き

URL は `<https://example.com>` または `[ラベル](https://example.com)` のように、クリック可能な Markdown リンクとして書く。リポジトリ内のファイルパスも `docs/foo.md _(cortex 内部参照)_` のようにリンクで参照する。

コード例・コマンド例として示す必要がある場合だけ、URL やファイルパスをインラインコードまたはコードブロックに入れる。

### 感覚的・主観的な品質基準

「きれいなコードを書く」「適切に設計する」のような基準。具体的で判定可能な基準として書く。lint ルールやテストで機械的に検証できるならそちらを優先する。

### 内部実装の詳細を含む MCP ドキュメント

MCP サーバーのドキュメントは利用者向け。利用者が知る必要のない実装詳細は書かない。書くべきはツール一覧、ユースケース、セットアップ手順。

### 陳腐化した技術スタック一覧

バージョン番号付きで列挙するパターン。`package.json`、`Pulumi.yaml`、Dockerfile がバージョン情報の正規の置き場所。docs/ には技術選定の理由（Why）だけを ADR で記録する。

## 整合性

### ドキュメント間の矛盾を残さない

同じ概念・閾値・ルール・設定値・用語定義が複数のドキュメントに登場する場合、すべての記述が同じ内容に揃っているか必ず確認する。矛盾を残したまま片方だけ更新すると、読者・AI エージェント双方が「どちらが正か」を判断できず、ドキュメント全体が信用を失う。

確認手順:

1. 変更ドキュメントの主題（用語・閾値・判定基準・ルール）を抽出する
2. Product Graph MCP の semantic search で同じ主題を扱う Document ノードを検索する: `search_product_graph_nodes(query: '<主題>', search_mode: 'semantic')`
3. ヒットした他のドキュメントの記述が変更後の内容と矛盾していないか確認する
4. 矛盾があれば、同 PR 内で全ドキュメントを揃えるか、正規の置き場所を 1 箇所に決めて他はリンク参照に置き換える（情報の正規化）

矛盾の典型例:

- 同じ閾値・上限値（coverage 90%、Slack 4 万文字、トークン上限等）が異なる値で書かれている
- 同じ用語が別のドキュメントで異なる定義・スコープで使われている
- あるドキュメントで「禁止」とした事項が、別ドキュメントで例外条件付きで許容されている
- 同じ判定基準が複数のガイドラインで異なる severity（Critical / Major 等）に紐付いている
- 手順・コマンド・パス・スタック名が複数のドキュメントで異なる表記になっている

| severity | scope | 観点 |
|---|---|---|
| Critical | ドキュメント変更を含む全 PR | 変更ドキュメントの記述が、参照される他ドキュメントの内容と矛盾していないか |
| Critical | ドキュメント変更を含む全 PR | severity / 禁止事項 / 閾値 など判定に直結する記述が、参照先ドキュメントと一致しているか |
| Major | 全 PR | 同じ概念が複数ドキュメントに重複記述されていないか（重複は矛盾の温床。1 箇所に統合してリンク参照に置き換える） |

矛盾検出は [severity.md](./severity.md) の「ドキュメント不整合」に該当し、Critical で `REQUEST_CHANGES` する。

## ライフサイクル

### 更新

ドキュメントの更新は、対応するコードの変更と同じ PR で行う。「後で更新する」は実質「更新しない」と同義。

### Markdown lint

`README.md` と `docs/**/*.md` は `markdownlint-cli2` で検証する。設定は
`.markdownlint-cli2.jsonc` に置き、`default: false` のまま cortex で必要な
ルールだけを明示的に有効化する。

有効化済みルール:

| ルール | 目的 |
|--------|------|
| MD007 | リスト indent を揃える |
| MD011 | reversed-link typo を検出する |
| MD024 | 同じ階層での重複見出しを防ぐ |
| MD034 | URL / メールアドレスを明示的なリンク表現にする |
| MD039 | リンクテキスト前後の余分な空白を防ぐ |
| MD041 | 文書の最初の見出しを H1 にする。Marp の HTML wrapper を許容するため `allow_preamble: true` |
| MD042 | 空リンクを禁止する |
| MD051 | fragment link の参照先見出しを検証する |
| MD052 | reference-style link の未定義参照を検出する |
| MD053 | 未使用 link reference を検出する |

MD025 / MD031 / MD040 は既存違反が多いため段階対応に分ける。MD003 / MD012 /
MD013 / MD030 など Prettier と責務が重なる整形系ルールは markdownlint 側では
有効化しない。

### 廃止

- 完了した計画書は `plans/archived/` に移動する
- 削除したアプリの対応ドキュメントも削除する
- 内容が現状と乖離し更新コストが見合わないドキュメントは削除する。git の履歴にあるので復元は可能

### 書くべきか迷ったら

| 質問 | Yes なら |
|------|---------|
| コードや型で表現できるか? | 書かない。コードに書く |
| lint ルールやテストで検証できるか? | 書かない。ルールを作る |
| 自動生成できるか? | 手書きしない。スクリプトを作る |
| 1 箇所だけ更新すれば済むか? | 正規の場所に 1 回だけ書く |
| 半年後も正確である自信があるか? | No なら書かない |
| 読者はこの情報なしで困るか? | No なら書かない |
