# 重要度分類・判定基準

## 重要度

| 重要度 | 基準 | アクション |
|--------|------|-----------|
| **Critical** | セキュリティ脆弱性、データ破壊リスク、本番障害の可能性、OOM リスク、**ドキュメント不整合**（対応ドキュメントの欠如、処理の追加・修正に伴うドキュメント未更新、既存ドキュメントと実装の乖離）、**`@graph-*` JSDoc の不一致・欠如**、**テストカバレッジ閾値の引き下げ**（vitest.config.ts の coverage thresholds を下げる変更は禁止。閾値を下げる代わりにテストを追加して基準を満たすこと）、**品質基準の緩和**（ガイドライン文書・lint ルール・カバレッジ閾値など品質基準を緩める変更。AI レビューはこれを含む PR を Approve せず `REQUEST_CHANGES` で差し戻す。人間レビュアーの Approve を必須とする） | `REQUEST_CHANGES` |
| **Major** | Composable Architecture 原則の違反、テスト欠如、パフォーマンス重大問題 | `REQUEST_CHANGES` |
| **Minor** | 命名改善、コメント追加、軽微なリファクタリング提案、パッケージ切り出し提案 | `REQUEST_CHANGES` |
| **Nit** | スタイル好み、微細な改善 | `APPROVE`（コメントで指摘） |

## 重要度の降格禁止ルール

以下のいずれの理由でも重要度を Nit に降格してはならない。該当 PR 内での根本対応を求める。

- **「既存パターンに従った追加」を理由にした降格禁止**: 既存コードがガイドラインに違反している場合、それに従った新規コードも同じ重要度で指摘する。「次回リファクタリング時に検討」のような先送りコメントは認めない。
- **「既存実装が違反しているので基準を合わせる」を理由にした品質基準緩和禁止**: 既存コードがすでに違反しているという事実は、ガイドライン・lint ルール・閾値を緩める根拠にならない。既存違反は別途修正すべき問題であり、基準側を下げることで解消してはならない。
- **「別 PR で対応」「次のセッションで対応」「スコープ外」「段階的に」を理由にした降格禁止**: 後回し・部分対応を前提に Critical/Major/Minor を Nit へ落とすことは禁止。後回し前提のコメントが author から提示された場合、reviewer は `REQUEST_CHANGES` で差し戻す。
- **TODO / FIXME 残置を理由にした降格禁止**: コード内の TODO / FIXME に残課題を書き残しても、それで重要度が下がることはない。レビュー指摘は該当 PR 内で根本原因まで直す。

例: 関数の引数が 3 つを超えている（オブジェクト引数にすべき）場合、既存関数が同じ違反をしていても **Minor**（`REQUEST_CHANGES`）として指摘する。Nit にしない。同様に、根本原因がアーキテクチャ違反であれば、表層パッチで「別 PR で根本対応」と提示されても降格せず `REQUEST_CHANGES` のまま扱う。

降格判断における例外条件はこのドキュメントには列挙しない。例外が必要な状況は都度判断し、合意内容を PR 上で明示する。

## マージ条件

全レビューコメントが resolved された場合のみマージ可能。APPROVE かつ未解決コメントがある場合はマージ保留。

## レビューコメントの方針

問題点・改善点のみを報告する。良い点の報告（「LGTM」「良い設計です」等のポジティブコメント）は不要。
